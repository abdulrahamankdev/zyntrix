# Zyntrix: Unidirectional Network Flow Threat Detection Prototype

## 1. Problem
Security monitoring systems frequently only have visibility into one direction of network-flow metadata (e.g., due to asymmetric routing or partial sensor coverage). The challenge is to identify cyber threats using only this limited unidirectional data without full packet inspection or bidirectional context.

## 2. Solution
Zyntrix provides a modular, multi-engine detection system designed to evaluate unidirectional flow metadata. It combines:
- **Rule Engine**: Deterministic security heuristics (e.g., known bad ports, volumetric anomalies).
- **Random Forest**: Supervised classification trained to identify known malicious traffic patterns.
- **Isolation Forest**: Unsupervised anomaly detection to flag unusual traffic behavior without requiring explicit labels.
- **Ensemble Engine**: A deterministic combination of these signals to produce a final classification (BENIGN, OUTLIER, or MALICIOUS) and a detection score.

## 3. Architecture
- **Frontend**: A React-based SOC dashboard that visualizes alerts, network relationships, and traffic volume.
- **API**: A FastAPI backend that handles flow ingestion and orchestrates detection.
- **Detection Pipeline**: Extracts features from flows and runs them through the Rule Engine, Random Forest, and Isolation Forest to produce an Ensemble score.
- **Evidence & Graph**: Detected threats generate an alert containing the extracted features, sub-scores, and explanations. The alert is cryptographically hashed (SHA-256) into a tamper-evident ledger. The communication relationships are visualized in a network graph.

## 4. Technology Stack
- **Frontend**: React (Vite, TypeScript, TailwindCSS)
- **Backend**: Python (FastAPI)
- **Machine Learning**: `scikit-learn` (RandomForestClassifier, IsolationForest)
- **Data Structures**: In-memory bounding queues (`collections.deque`), `networkx` for graph generation.

## 5. Data and Training
The prototype currently uses **synthetic network flow data**. 
- The Random Forest is trained on a generated dataset containing labeled normal, scanning, exfiltration, and DDoS behaviors (`data/train_labeled.json`).
- The Isolation Forest is trained strictly on benign baseline traffic (`data/train_benign.json`).
- The system is evaluated and demonstrated using a separate, controlled test stream (`data/test_stream.json`).
*Note: This data represents a simulated, controlled distribution and does not currently utilize real-world public datasets like CICIDS2017.*

## 6. How to Run

### Requirements
- Python 3.10+
- Node.js 18+

### Setup & Run Backend
```bash
# Navigate to backend
cd backend

# Install dependencies
pip install -r requirements.txt

# Start the API server
python main.py
```
*The backend runs on http://127.0.0.1:8000.*

### Setup & Run Frontend
```bash
# Navigate to frontend
cd frontend

# Install dependencies
npm install

# Start the development server
npm run dev
```
*The frontend runs on http://localhost:5173.*

## 7. 5-Minute SIH Demonstration Sequence

1. **Explain the Problem (0:00–0:45)**: Explain that security monitoring often has access only to one direction of network-flow metadata.
2. **Show Architecture (0:45–1:30)**: Explain the flow: Rules → Random Forest → Isolation Forest → Ensemble.
3. **Start Demo (1:30–2:30)**: Open the Zyntrix Dashboard and click "START LIVE DEMO". Show the live traffic volume, active alerts appearing, and the Interactive Network Graph.
4. **Open a Malicious Alert (2:30–3:30)**: Click an alert in "Threat Alerts". Show the extracted features, rule evidence, RF probability, IF anomaly signal, ensemble score, and the final attack classification.
5. **Evidence Ledger & Tamper Verification (3:30–4:15)**: Go to the "Evidence Ledger" page. Show that the original alert passes the hash check (`PASS`). Then manually explain how modifying a single value in the alert (e.g., classification) would break the cryptographic verification (`FAIL`).
6. **Evaluation & Limitations (4:15–5:00)**: Present the evaluation results generated by `python backend/evaluate_model.py`. Explain the limitations (synthetic data) and the future plan for real-world deployment.

## 8. Evaluation Benchmark
Current performance on the synthetic test stream (Strict 3-Class Classification):
- **Ensemble Accuracy**: 85.20%
- **Macro F1**: 83.43%
- **Weighted F1**: 85.52%
- **BENIGN Recall**: 100%
- **OUTLIER Recall**: 100%
- **MALICIOUS Recall**: 63% (with 74 missed flows classified as OUTLIER)
- **BENIGN → Threat Error**: 0 False Positives

*(Generated via `python backend/evaluate_model.py`)*

## 9. Limitations
- **Data Validity**: The current benchmark measures performance on a controlled synthetic distribution, not unseen real-world network traffic. The synthetic data generation uses bounded heuristics rather than true network packet capture.
- **Memory/State**: The prototype utilizes in-memory bounded queues for storage. It is not currently backed by a persistent database (e.g., PostgreSQL/MongoDB).
- **Security**: The API currently lacks authentication, assuming a trusted network environment for the prototype demonstration.

## 10. Future Work
- **Real-World Data Integration**: Implement data adapters to ingest and validate against actual public datasets (e.g., CICIDS2017, UNSW-NB15) by extracting features directly from PCAP files using Zeek.
- **Persistent Storage**: Migrate in-memory ledgers and graphs to a robust database structure (e.g., PostgreSQL for alerts, Neo4j for the graph).
- **Authentication**: Add JWT-based authentication for SOC analysts.
